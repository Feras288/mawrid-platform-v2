## 2. مراجعة Store Catalog View (عزل البيانات)
- العرض يكشف فقط: منتجات منشورة ونشطة لها سعر تجزئة ساري، لموردين ملفهم «معتمد» **ومؤسستهم نشطة**.
- الأعمدة المكشوفة لا تتضمن مخزوناً أو تكلفة أو أسعار الشركات/التعاقد/المناطق أو بيانات المشترين؛ `store_price` = أقل سعر تجزئة فقط وتكتبه triggers بصلاحية المالك.
- صلاحية `app_user` على العرض قراءة فقط، والصفوف تُعاد قراءتها تحت RLS الخاص بالمستخدم.
- **عيب مؤكد وأُصلح:** تعليق المسؤول لمؤسسة مورِّد لم يكن يخفي منتجاتها وأسعارها (ولا يمنع إرسال طلبات التسعير لها)، لأن فحص الاعتماد كان يقرأ حالة الملف فقط. الآن تشترط دوال الاعتماد والعرض ومسارات RFQ أن تكون المؤسسة نشطة، ويُعاد الفحص لحظة تسليم RFQ.
- اختبارات أمنية جديدة (`catalog-security.int`، 5 اختبارات): إخفاء غير المنشور/غير النشط/غير المسعّر، عدم تسرب الأسعار غير العامة، إخفاء المورد المعلّق في المتجر والسلة وRLS ودليل الموردين والمستلمين والتسليم، العرض للقراءة فقط وبدون أعمدة خاصة.
- مخاطرة مقبولة وموثقة: العرض ليس `security_barrier` حفاظاً على استخدام الفهارس؛ لا يمكن استغلال ذلك إلا بجلسة تنفذ SQL حراً، وهذا غير متاح لأي مستخدم.

## 3. سلامة المستودع
- كل التغييرات محفوظة في Git (شجرة العمل نظيفة بعد آخر commit).
- لا أسرار أو مفاتيح أو نسخ قواعد بيانات متتبَّعة؛ الملف الوحيد من نوع env هو `.env.example` بقيم تطوير وهمية. لم يُضَف أي `.env` حقيقي في سجل Git.
- أُضيف `infra/backups/` و`*.dump` إلى `.gitignore` حتى لا تُرفع النسخ الاحتياطية بالخطأ.
- قاعدة التطوير المحلية فقط تحتوي ~100 ألف منتج اختباري (لأغراض قياس الأداء)، وليست في المستودع.

## 4. الجاهزية لـ CI وبناء صور Docker على GitHub
- `.github/workflows/ci.yml`: مهمة `checks` (typecheck، lint، unit، تحقق من الترحيلات والانحراف، integration، audit، build) ثم مهمة `images` تبني صورتي web وworker **دون push**.
- أُصلح عائقان مؤكدان كانا سيُفشلان بناء صورة الويب: (1) `next build` كان يتطلب `DATABASE_URL` → أصبح اتصال قاعدة البيانات كسولاً؛ (2) TypeScript لم يكن ضمن تبعيات تطبيق الويب عند التثبيت المُرشَّح → أُضيف.
- لم يُنفَّذ أي push أو نشر. التشغيل الفعلي لـ CI يحتاج موافقتك على رفع المستودع إلى GitHub خاص.
- ملاحظة: اختبارات E2E غير مدرجة في CI (تحتاج خوادم وبيانات seed)؛ يُوصى بتشغيلها على Staging.

## 5. المخاطر الحرجة (قبل الإنتاج)
1. **قرارات العمل غير محسومة** (البائع النظامي DEC-01، مزود الدفع DEC-02، نموذج الإيرادات DEC-03، مُصدر الفاتورة الإلكترونية DEC-06، موقع الاستضافة DEC-05): الدفع الحي والتسويات معطلة حتى تُحسم.
2. **صور Docker لم تُبنَ فعلياً بعد**: كل خطواتها مُختبرة محلياً، لكن أول بناء حقيقي سيكون في CI أو على خادم Staging.
3. **ZATCA المرحلة الثانية (فاتورة)** غير متكاملة؛ المتوفر بيانات المرحلة الأولى ورمز QR فقط.
4. **النصوص القانونية** مسودات تحتاج مراجعة قانونية.
5. **CSP** يسمح بـ `'unsafe-inline'`، وتحذيران متوسطان في `pnpm audit` في مسارات غير مستخدمة وقت التشغيل.
6. **لا توجد بيئة Staging** ولم تُختبر النسخ الاحتياطية خارج الجهاز المحلي.

## 6. متطلبات تشغيل Staging
1. موافقتك على رفع المستودع إلى GitHub خاص وتشغيل CI (للتحقق من بناء الصور).
2. خادم Coolify (يُفضل داخل المملكة) بذاكرة ≥ 4 GB، ونطاق staging (مثل `staging.<domain>`) مع TLS.
3. أسرار Staging منفصلة عن الإنتاج: `AUTH_SECRET`، `APP_ENCRYPTION_KEY`، `POSTGRES_OWNER_PASSWORD`، `APP_DB_PASSWORD`.
4. حاوية S3 خاصة بـ Staging مع تفعيل versioning، وحساب SMTP تجريبي (أو Mailpit داخلي).
5. مزود الدفع: `PAYMENT_PROVIDER=test` غير مسموح في `production` فقط؛ يمكن استخدامه في `APP_ENV=staging`، أو مفاتيح Moyasar sandbox إن توفرت.
6. بعد النشر: تشغيل `migrate`، إنشاء حساب مسؤول وتفعيل 2FA، ثم تشغيل مجموعة E2E ضد Staging وجدولة النسخ الاحتياطي واختبار الاستعادة.
7. التفاصيل الكاملة في `docs/DEPLOYMENT.md`.
